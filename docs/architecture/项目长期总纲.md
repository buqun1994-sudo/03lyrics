# 03lyrics 项目长期总纲

## 1. 项目定位

1. `03lyrics` 是面向 iCAR 03 车机的轻量悬浮歌词应用。
2. 核心结果：从播放器公开的 Android MediaSession 获取播放信息，匹配同步歌词，并根据原厂桌面状态在顶栏或壁纸区域安全显示。
3. 正式运行不依赖 root、ADB、手机、电脑或自建后端；壁纸歌词的 SR 早期避让与按实际位置选择 Dock 裁剪依赖用户或受控部署明确启用的只读无障碍服务，该服务不读取文字、不执行节点动作或手势。
4. 本项目基于 `tcrrry/desktop-lyrics` 的历史继续适配；上游只作为来源追溯，当前默认远端为项目自己的 GitHub 仓库。

## 2. 平台基线

1. 目标车机：Android 9（系统 SDK 28）、`1920 x 1080`、型号标识 `S56_HQX`、高通 8155。
2. 工程基线：Kotlin Android，JDK 17，Gradle 8.2，Android Gradle Plugin 8.2.2，`compileSdk/targetSdk 34`，`minSdk 26`。
3. 当前应用身份：正式 `applicationId/namespace = com.ninepointnine.desktoplyrics`；Debug/staging 通过 `applicationIdSuffix=".test"` 派生 `com.ninepointnine.desktoplyrics.test`，并追加 `versionNameSuffix="-test"`；诊断变体通过 `applicationIdSuffix=".diagnostic"` 派生 `com.ninepointnine.desktoplyrics.diagnostic`，并追加 `versionNameSuffix="-diagnostic"`。Release、Debug、staging/test 和 diagnostic 共用根目录 `release-version.properties`，当前正式版本为 `1.0.10-icar03` / `versionCode=124`，测试版本为 `1.0.10-icar03-test` / `versionCode=124`，诊断版本为 `1.0.10-icar03-diagnostic` / `versionCode=124`。
4. 车机整体负载偏高，新增能力必须保持事件驱动、固定尺寸资源缓存和低绘制成本。

## 4. 运行状态流

1. 任何由 `startForegroundService()` 创建的 `LyricsOverlayService` 都先创建通知渠道并立即调用 `startForeground()`；授权判断、运行资源创建、恢复退化、停止和异常处理全部发生在前台契约之后。
2. 服务集中读取启动来源、悬浮权限和通知使用权，并通过唯一启动策略进入 `RUNNING / RECOVERY / COMMERCIAL_RECOVERY / USER_STOPPED`；日志只记录判定字段和最终状态，不记录媒体内容或用户数据。
3. 两项授权有效时清除旧恢复通知并沿唯一服务实例启动 MediaSession、车机监听和唯一 WebView/窗口。任一授权缺失时释放歌词运行资源、结束前台服务且返回 `START_NOT_STICKY`，保留 `PREF_AUTO_START`，并留下可点击进入现有 `MainActivity` 的常驻恢复通知；下一次授权有效的合法启动会清除该通知并重新进入同一运行主链。
4. 播放器变化经 MediaSession 回调进入统一仲裁；按 `USAGE_MEDIA`、内容类型、传输动作、标题及播放状态排除自身和语音 / 提示音。冷选与上次来源恢复共用“播放 / 缓冲 / 有标题的暂停”条件，`STATE_NONE`、停止、错误或未知状态不能凭历史偏好进入主链。当前暂停会话保持粘性，停止历史会话不重新接管。所有候选回调进入合并重选，当前来源同时刷新快照；来源变化后以 `250ms / 1000ms` 两次有界复核收敛。`MediaSessionMetadataPolicy` 以 `DISPLAY_TITLE` / `DISPLAY_SUBTITLE`、`MediaDescription`、原始 `TITLE` / `ARTIST` 的稳定优先级提取歌名和完整歌手，`ALBUM` 只解释为专辑；不拆连字符，歌词和动态制作信息不参与身份。选中来源交给 `MediaPlaybackAdapter`，先补齐同来源、同公开 ID 和相同归一三字段下已观察的缺失时长，再交给 tracker；两个非空公开 ID 不同或既有字段冲突时切换录音代际，ID 后补不重复查词。字段补齐或已知时长相对上次查询累计变化超过 `2000ms` 只推进查询修订。每个当前状态都交给 `LyricsPlaybackStore`，幂等与取消由 Store 拥有；先查缓存，未命中或过期再调用现有协调器。
5. 标准和蓝牙进度共用 `MediaSessionTimelineTracker`：只有 `0 < lastPositionUpdateTime <= elapsedRealtime` 才是有效发布时刻，其它变化位置按回调时刻处理；未知位置保留已建立的时间线，首次未知保持 `timelineReady=false`。正在播放且歌词已可用时，WebView 先预览第一句且不推进，可信位置到达立即定位。AVRCP 事件绑定录音代际，未来、旧代际或超过 `1500ms` 的事件丢弃；事件重锚后，重复旧位置和仅更新时间戳的同值帧不得回滚进度。暂停冻结、seek、切歌和时长封顶均由该 owner 处理；运行态重建和销毁取消旧连接及所有歌词任务。

   公开歌曲事实只持久化实际观察到的 `1000..86400000ms` 时长，最多 `128` 条且只在事实改变时写入；来源、非空 ID 和归一三字段全部相等时只补 `0ms`，任何正实时值优先。Adapter 用原始发布时长判定位置证据：时长不可用且位置为零时视为未知，实际正位置或带有效时长的零位置可重锚，AVRCP 显式零位置仍有效。检查点保留 `24h`、同来源 / 三字段 / 时长差不超过 `2000ms` 的门槛；任一方含公开 ID 时双方 ID 必须完全相同，不给旧检查点猜补 ID。恢复位置仍交给同一时间线，不从重启间隔推测停车期间的播放。
6. `LyricsResolutionSession` 按来源实际完成顺序把目录候选交给 `LyricsCandidateSelector`；某个目录来源当前查询没有可用候选时只推进该来源的下一项搜索计划，不等待其它慢来源。首个通过显式准入且正文为同步歌词的结果立即返回。无可信结果保持静默；仅瞬时网络、限流、服务端或截止失败等待 `1000ms` 后重试一次，完成无匹配和元数据无效不重试。
7. `IcarDisplayStateMonitor` 把原厂启动器状态映射为 `DESKTOP` 或 `TOPBAR`，并事件驱动监听 `window_mode`：`0/1` 表示桌面歌词区域无系统窗口冲突，`2/3` 包含标准浮窗冲突；其它值或读取失败保守映射为 `TOPBAR`。同一适配器监听 `global_setting_ac_page_status`：`1/3` 为占用，`2` 为完全收起，其它值或读取失败为未知；占用和未知均隐藏全部歌词。
8. `IcarDockAccessibilityService` 只在 Launcher 窗口或结构变化时读取交互窗口边界和资源 ID 为 `com.mengbo.launcher3:id/adas_handler_view` 的 SR 把手矩形；系统 `80ms` 事件合并后立即读取，相邻位置横向变化达到 `max(4px, 屏宽/240)` 即发布展开或收回方向提示，目标车机阈值为 `8px`。最后一次事件后 `320ms` 复核终态并清除瞬时提示，由 `window_mode` 的稳定占用继续兜底。分类器识别左、中、右三个 `25%..40%` 宽度且贴下边界的 Dock 窗口。`LyricsOverlayService` 将两类 SR 信号、Dock、设置页、租约、启动器、标准窗口和用户偏好交给 `IcarLyricsPresentationPolicy` 全量重算：租约和标准浮窗切顶栏；左侧原位采用左 Dock，被 SR 推到右侧安全位置后采用中间 Dock，右侧位置始终采用右 Dock；左侧壁纸按方向提示立即启动 `250ms` 先快后慢位移，不跟随手势百分比；空调页隐藏全部歌词，未知有效 Dock 在壁纸态保守切顶栏。空调关闭后不保存或回放旧 presentation，而是立即以最新原车窗口状态重算唯一表面。
9. `ACTION_STOP` 只表示用户主动停止当前运行态，不修改自动恢复意图；授权失效只进入恢复态。开机或应用升级广播只有在用户保存的该意图仍为真时才请求恢复服务。
10. Android 标准 `Configuration.uiMode` 是深浅主题唯一真值：设置页由 `values` / `values-night` 自动选色；常驻服务在配置变化时只向 WebView 下发 `light` / `dark`，不重载歌词页和播放时间线。
11. 设置页现有代码只读监听 `com.mb.provider.theme_key`，由 `IcarThemeColorPalette` 尝试映射原车色板；最新用户主测结论为主题色没有适配成功，因此该链路保持未完成状态，不改变深浅主题已经验收通过的结论，也不写车机设置或进入歌词服务、WebView 主链。
12. 设置页只在进入时通过 `NotificationManagerCompat.getEnabledListenerPackages()` 和 `Settings.canDrawOverlays()` 判断服务能否启动；“服务状态”页展示当前运行开关与一次性重启动作，不展示授权状态或跳转系统授权页。“开机自启动”默认开启且仍是独立持久偏好，持久化写入只允许设置页的该开关，开机接收器和运行态只读取它；普通服务启动、重启和 `ACTION_STOP` 均不得改写。当前目标固件的敏感设置页会过滤被常驻覆盖窗口遮挡的触摸，授权属于应用外部的受控部署前置条件；`MainActivity` 保持普通 `singleTop` 启动模式。
13. `ACTION_RESTART` 只由 `LyricsOverlayService` 处理：同一服务实例先使旧运行代际失效，再注销 MediaSession、音频、AVRCP 与车机状态监听，移除并销毁唯一 WebView/窗口，重新读取显示偏好并重建运行资源；不经过 `ACTION_STOP`，不改变 `PREF_AUTO_START`。
14. 顶栏当前行在 `lyrics_overlay.html` 内同时保存“显示索引”和“是否到达该行时间点”：下一句可沿用现有 `90ms` 提前量切入画面，但主行横向滚动资格只在原始时间戳到达后开放。第一句在前奏阶段只预览不滚动；跳播回时间点之前时，同一行关闭滚动资格并复位，调度器必须分别唤醒“提前切行”和“准确到点”两个事件。切行只允许重算新当前行的横向动画；退出行保持既有位移直至移除，避免长句从末尾反向回滚。
15. 顶栏与桌面歌词共用同一个原生悬浮窗根表面；表面切换由 `LyricsOverlayService` 唯一编排为旧表面 `120ms` 线性淡出、完全透明时提交窗口几何与 WebView 布局、新表面 `160ms` 线性淡入。动画期间窗口不可触摸，快速连续切换只允许最新目标完成回调；WebView 不维护第二套表面交接状态。
16. 桌面歌词的上下边缘渐隐归 `lyrics_overlay.html` 呈现层所有：只对桌面 `.lyrics-viewport` 使用 `64px` 线性 alpha mask，中部保持完全不透明，顶栏不继承。外层 Dock 裁剪时，`LyricsOverlayService` 只按可见高度比例更新 mask 的底部终点，完整歌词布局高度不变；该能力不增加定时器、逐帧脚本、动态模糊或额外歌词状态，性能验证以“无持续重绘、帧耗时无明确回退”为不变量。
17. 桌面歌词换句由 `lyrics_overlay.html` 一次性提交最终活动行、真实 `42px / 58px` 字号及最终模糊 / 阴影状态，再用 `220ms` FLIP 过渡歌词容器与受影响行的 `transform` / `opacity`；只对原文做逆向缩放，翻译保持独立真实字号。`font-size`、`filter`、`text-shadow`、颜色和 alpha mask 不参与逐帧插值；跳播、触摸、偏好、尺寸、主题、表面或翻译状态变化必须取消唯一临时动画 owner 并清除内联样式。
18. 顶栏与壁纸字号分别持久化；升级时只把旧单一字号作为两项尚未存在时的初始值。壁纸模糊和全句阴影默认开启、排版默认标准、焦点默认中间；阴影关闭时所有歌词均无阴影，开启时所有歌词均有阴影。“顶部”内部目标为可视高度约 `15%`，位于固定渐隐带下方，不把当前句放入边缘透明区。
19. 人工查找由 `LyricsOverlayService` 绑定搜索开始时的当前播放身份，LRCLIB / QQ / 网易云并行返回每来源最多 `8` 条、合计最多 `24` 条候选。人工候选只排序、不复用自动准入淘汰；正文只在点选后读取，非同步正文拒绝写入。切歌、搜索代际变化、服务重建或用户再次搜索都会取消旧任务和可断开连接，旧回调不得覆盖新状态。
20. 设置状态通过包内显式广播返回，正文不离开服务 / 缓存主链。人工选择成功后由 Store 写入人工覆盖、回读并发布同一歌词 / 缓存快照；恢复自动只删除该人工覆盖。删除当前缓存清除当前身份的自动与人工记录，可以保留已加载歌词并标记“尚未缓存”；读缓存中与未缓存必须区分。总容量达到 `128 MiB` 时由 `LyricsCache` 淘汰，无全量删除动作、广播或数据库 API。
21. `scheduleWebDispatch` 是唯一播放 / 歌词投递入口，检查运行代际、目标 WebView 实例、录音代际和查询修订；一次 `evaluateJavascript` 先提交播放再提交对应歌词。相同正文不因进度或统计更新重复发送、解析，WebView 不再回调请求自动歌词。Debug 可用标准 WebView 检查与不含歌词正文的状态日志观察同一快照。

### 4.0 媒体通道基线

1. 目标车机只读 `dumpsys media_session` 已观察到：蓝牙 `com.android.bluetooth/A2dpMediaBrowserService`；本机音乐 `com.tencent.wecarflow/com.mengbo.service.play.customplayer.HddPlayerService`；U 盘 `com.tencent.wecarflow/com.mengbo.service.play.customplayer.UsbPlayerService`；爱趣听会话 `com.tencent.wecarflow/.player.MediaPlaybackService`（固件组件名以公开会话为准）；以及其它公开媒体会话。前四类的公开音频属性均为 `USAGE_MEDIA / CONTENT_TYPE_UNKNOWN`，因此选源能力不按包名白名单裁决；仅在已验证的蓝牙 AVRCP 元数据 / 时间线适配边界读取其传输画像。
2. `MediaSessionManager` 返回的系统会话顺序是同一活动等级下的唯一 tie-breaker；服务同时观察全部候选控制器，任一候选状态、元数据、音频信息或会话销毁变化都以 `80ms` 合并窗口触发重读。`MediaSessionArbiter` 保留当前会话身份：当前会话离开活动列表仍以 retained controller 参与评估，暂停会话继续保持；播放中挑战者只有在 `250ms` 内位置或 `lastPositionUpdateTime` 出现新进度才确认交接，冷启动最多等待 `1500ms` 收敛唯一暂停来源。会话销毁后开启 `5000ms` 同源重绑定窗口；同包新 Token 到达则保留录音代际和歌词，窗口到期才清除当前身份。来源变化后仍以 `250ms / 1000ms` 两次有界复核收敛，另有 `5s` 低频兜底刷新。`AudioManager.AudioPlaybackCallback` 只作为重读唤醒信号，不消费配置内容；设置打开、设置状态请求、人工搜索 / 点选、恢复自动和清理缓存均先同步重读 MediaSession，再发布或绑定当前歌曲。该监听只消费公开回调，不读取通知正文或系统音频；已有来源停止或消失后不从暂停旧会话回接。
3. 控制器元数据先经过 `MediaSessionMetadataPolicy`，再进入录音、设置、缓存、查词或 WebView：`DISPLAY_TITLE` / `DISPLAY_SUBTITLE` 优先提供展示用歌曲名与歌手，`MediaDescription` 和原始 `TITLE` / `ARTIST` 只作稳定回退；`ALBUM` 仍只解释为专辑名。03T 媒体中心可能把原始 `TITLE` 轮换为制作信息，不能无条件使用它。`BLUETOOTH_AVRCP` 只保留时长单位归一与已验证的位置 / 状态补偿，不改变标题、歌手、专辑语义。Adapter 内的 `MediaRecordingStateTracker` 唯一拥有录音代际与查询修订，设置页和 WebView 只消费下发代际，不自行拼文本键。
4. `MediaSessionTimelineTracker` 使用 `SystemClock.elapsedRealtime()` 作为统一时基；新录音首帧超过 `2500ms` 的旧位置保持未就绪，标准冷启动可以使用当前有效位置，蓝牙重复零值不能建立可信时间线。AVRCP 位置重锚同一 owner，之后控制器的变化位置必须携带更新的有效时间戳；重复同值帧不能回滚。检查点恢复后的蓝牙继续等待 AVRCP 确认。未知进度只限制真实逐句推进，不阻止第一句预览；暂停冻结，seek、切歌、速度变化或时长封顶按同一规则处理。
5. `PublicMediaBrowserSessionRegistry` 统一发现已导出的公开 `android.media.browse.MediaBrowserService`：启动后 `30000ms` 冷发现窗口内最多连接 `8` 个服务，窗口结束后只连接当前活动包、上次稳定来源和蓝牙服务；若仍无已选来源，继续有界发现。发现列表保持完整，准入过滤后优先分配上次稳定来源、当前活动包，最后分配其它合格服务，同级保持发现顺序；`8` 个连接的上限只能在该分配阶段应用，不能提前丢弃尾部的恢复来源。蓝牙输出路由仅作重读提示，不是 Browser 连接门槛。每服务 `3000ms` 超时、最多一次 `1000ms` 重试，断开和迟到回调隔离由同一注册表负责，控制器按 Token 去重后追加到系统列表末尾。爱趣听、本机、U 盘、03T 内置网易云代理和蓝牙共用该适配与仲裁。Android 9 蓝牙保持毫秒，Android 10/11 蓝牙使用已验证的秒到毫秒归一，其余服务按毫秒，封顶 `86_400_000ms`。
6. 检查点以包级来源、歌名、完整歌手、专辑、时长和保存时间绑定录音；有效期 `24h`，双方时长至少 `1000ms` 且差值不超过 `2000ms`，缺失歌手 / 专辑不作为通配符。只在实时位置未知时恢复，断电期间不外推；第一句预览不得保存为进度，用户主动停止清除检查点。来源重选合并为 `80ms`，当前播放快照合并为 `35ms`，沿用 `5000ms` 低频发现，不增加高频轮询。
7. `MediaPlaybackAdapter.kt` 内的 `AvrcpPlaybackEventDecoder` 唯一声明已取证广播及字段，Receiver 直接以同一动作集合注册：`PLAYBACK_POS_CHANGED` / `PLAYBACK_POS_CHANGEDS`、`TRACK_EVENT`、`PLAY_STATUS`、`PLAYBACK_STATUS_CHANGED`。完整 `PLAY_STATUS` 从 `extra.SONG_POS` / `extra.SONG_LEN` 取得毫秒位置和时长，`PLAYBACK_STATUS_CHANGED` 可提供位置或原始 AVRCP 状态；`profile.extra.PLAYBACK` 使用 Android 状态语义。状态 / 元数据事件缺少位置时不得制造零值，位置只接受 `0..86_400_000ms` 整数并拒绝未知哨兵。完整快照的有效时长与当前录音相差超过 `2000ms` 时整帧拒绝，状态和位置由 Adapter 绑定同一录音并输出 `MediaPlaybackFrame`；服务不再持有第二份蓝牙状态。iPhone 与 Android 的事件差异在该协议边界消化，不按手机品牌或音乐平台分支。

### 4.1 商业权益状态流

1. `LyricsOverlayService` 仍先履行 Android 前台服务时限。每个新的服务生命周期同步读取一次 `CommercialAccessGate`，并异步通过一次性设备签名 challenge 调用 `POST /v1/products/{productId}/device-access/license/check`；即使系统授权缺失而即将进入授权恢复态，复核仍由进程级单飞任务完成。系统授权仍是歌词资源创建的第一道门禁，只有系统结果为 `RUNNING` 且本地商业结果为 `Allowed`，才调用 `ensureLyricsRuntimeResources()`。
2. 每个新的设置页实例继续执行完整权益查询。完整查询与服务轻量复核共享 `SingleFlightCommercialEntitlementCheck` 的同一核心请求；`active` 不签发新许可证、不生成 `licenseId`、不改写本地许可证字节或时间。设置页在核心权益结果后才读取待支付会话和活动报价，服务启动不访问活动或报价接口。
3. 本地有效许可证使歌词立即运行，云端复核不阻塞启动；网络、限流、超时、服务端异常或其它非权威失败只重新读取并尊重本地门禁，同时写入待复核标记。若本地无效，服务保持前台契约但不创建歌词 owner，等待当次复核；云端返回并持久化新的签名试用或永久 PRO 后恢复一套资源，复核失败则进入 `COMMERCIAL_RECOVERY`。试用短租约到期但固定七天仍有效时，用当前设备密钥取得下一张最长 `24h` 的试用许可证；永久 PRO 没有本地过期或离线宽限。`CommercialRuntimeAccessGuard` 只保存统一门禁已返回的单个 `Allowed?`，最终 denied 在回调前先清空运行许可，不得从 UI 权益状态或设置动作旁路放行。
4. 商业拒绝进入独立 `COMMERCIAL_RECOVERY`：关闭并清空已经存在的歌词仓库、协调器、缓存、协程、MediaSession、WebView、窗口和车机监听，结束前台服务并留下进入“权益”分类的恢复通知；`PREF_AUTO_START` 保持原值。重新获准后才从 `ensureLyricsRuntimeResources()` 重建，不预留空转 owner。
5. 云端返回 `revoked` 时，许可证仓库先写入加密撤销标记并使本地凭证 fail closed，同时清除许可证、device token、待支付和待复核状态；运行服务释放仓库、协调器、缓存、协程、MediaSession、WebView、窗口和监听。云端返回 `active` 只确认当前权益，不签发或替换许可证；试用租约到期时才用当前设备密钥请求下一张短租约。`not_started` 时不得静默沿用本地权益：没有本地许可证时进入试用开始，本地仍有试用时使用原始首次打开时钟重新建立云端试用，本地 PRO 凭证则收敛为撤销；`device_key_mismatch` 才调用一次同指纹恢复。网络、验签或持久化失败保留仍有效的本地凭证并在下一生命周期重试。最终撤销时设置页 Controller 先发送专用 `REVOKED` 再渲染错误，启动复核直接进入 `COMMERCIAL_RECOVERY`；权益主页把撤权解释为可重新购买状态，用户点击“获取Pro”后重新请求服务端报价，而不是重复权益查询。
6. 领域页固定映射为：`Hidden / Paid -> ENTITLEMENT`，`Details / CreatingPayment / Expired / Error -> ORDER`，`AwaitingPayment -> QR`。状态机另持有 `ENTITLEMENT / ORDER / QR` 页面 owner：权益首页和订单页由用户显式导航持有，二维码页由当前支付操作持有；晚到的权益快照、报价、建单或轮询结果不得覆盖当前 owner。只有新生命周期清空 owner 后，持久化的待支付会话才可恢复二维码；PRO、撤权和其它权威拒绝仍强制回权益页。广告横幅动作只派发 `EntitlementPageRequested`，不会派发 `CheckoutRequested`；系统返回在订单或二维码页先消费为回权益主页，不直接关闭设置窗口。
7. 试用、过期、PRO、首次查询和查询错误彼此区分。已稳定的 PRO 在后台刷新期间保持 PRO，不重新显示广告；最终非 PRO 结果才替换。PRO 生效后整个广告容器为 `GONE`，不存在高度占位。
8. `ProductQuote` 的 `quoteId`、原价、比例、折扣、计算金额、最终金额、最低支付标记、支付方式和有效期全部来自 API。状态机只选择和传递这些字段；输入未应用时不修改旧报价，客户端不做乘法、舍入或成交价推导。
9. 当前公开活动先经 `campaigns/current` 读取，再用返回码创建短期报价。无效 / 过期 / 不可用码仍接收原价报价；`quote_changed` 必须展示 `latestQuote` 并等待第二次确认；`already_owned` 直接保存许可证并进入 PRO。
10. 支付会话将 poll token 与二维码会话加密持久化，Activity 重建后可恢复。Controller 按服务端 `pollAfterSeconds` 自动轮询；离开二维码页立即结束当前轮询代际，迟到结果失效，网络或限流只在仍由该支付会话持有的二维码页显示暂时状态并继续；支付成功后先保存 `deviceToken` 与已验签许可证再开放 PRO。
11. Debug fixture 在原始 HTTP / JSON 边界模拟全部九个接口，并验证设备签名与轮询原文；默认报价为 staging 小额边界。Debug 专属 Activity extras 不出现在正式页面，Release 不携带 fixture 金额、活动码、二维码域名、签名键或成功响应。
12. API 基址只由构建变体装配：Debug 默认 `fixture`；显式 `staging` 固定使用 `https://api-staging.9studio.fun` 且必须同时注入 staging 公钥、`keyId` 与实际 APK signer SHA-256；Release 的 production 基址、公钥、`keyId` 与正式 signer SHA-256 必须显式注入。非 fixture 运行时在进程内只读取一次当前 signer 并与预期摘要匹配；本地构建不会因存在网络类而自动访问任一远端环境。

### 4.2 设备身份与许可证不变量

1. 初始设备签名键为 P-256 AndroidKeyStore 别名 `03lyrics_device_key_v1`；恢复换钥使用持久化的待确认别名。公开信息只导出 SPKI、公钥 SHA-256、签名证书 SHA-256 和设备指纹；设备指纹固定为 `SHA-256(ANDROID_ID)`，客户端不再显式把产品、包名或 APK signer 拼入指纹，相关身份继续通过独立契约校验。
2. challenge 的 `signatureBase64` 固定签 Base64 解码后的 32 字节原文，不增加帧头。轮询固定签 UTF-8 文本 `purchaseId + "\n" + pollToken + "\n" + timestampSeconds + "\n" + nonceBase64Url`；nonce 至少 16 字节并且每次重建。设备私钥不导出，Key Attestation 仍只作非阻断能力探测。
3. 许可证先对 `payloadBase64` 解码出的原始 JSON 字节执行 `SHA256withECDSA`，通过后才解析并核对 envelope / payload / 配置三方 `keyId`、版本 `1`、产品、当前公钥摘要、设备密钥版本和时间边界。永久 PRO 必须为 `validity=permanent` 且 `expiresAt`、`offlineGraceUntil`、`trialEndsAt` 明确为 `null`；试用必须为 `validity=trial`，`expiresAt` 与 `offlineGraceUntil` 最长 `24h` 且不超过固定七天 `trialEndsAt`。
4. 许可证、权益撤销标记、待复核标记、device token、poll token、未完成支付会话、首次打开时钟、许可证可信时间、设备密钥版本、活动密钥别名和待确认恢复别名使用独立 AES-GCM AndroidKeyStore 别名 `03lyrics_commercial_storage_key_v1` 加密，按记录名作为 AAD 写入 `noBackupFilesDir`；应用整体关闭 Android 备份。撤销标记优先于任何仍存留的许可证；新的有效签名许可证完成持久化后才允许重新开放门禁。
5. 首次试用必须联网取得云端签名许可证；本地首次打开时间只作为请求输入，不能授权歌词资源。重复请求、进程重建、重装或同指纹换钥均以云端原始试用起止为准，客户端只接受签名 `trialEndsAt`。
6. 恢复时，已有已知云端 key 版本则生成待确认新钥并用旧钥对同一 challenge 附签；旧钥 / 本地版本不存在时用当前新钥走同指纹恢复。启动权益查询只有在云端明确返回 `device_key_mismatch` 时自动调用现有恢复主链一次；`device_fingerprint_mismatch` 与其它安全失败不进入恢复，自动恢复结果也不得递归。待确认别名在网络响应丢失后保留并复用，成功后才切换活动别名、保存新版本并清理旧钥。
7. 任何启动、新的歌词服务生命周期、用户点击重启服务或打开新的设置页都先读取本地签名许可证，并通过同一 `CommercialEntitlementCoordinator` 单飞调用 `license/check`。`active` 保持本地许可证原始 bytes、`licenseId` 和时间不变；`revoked` 清除本地许可证、device token、待支付 / 待复核状态并释放运行资源；网络失败保留仍有效凭证并记录待复核，下一次生命周期再试。试用租约到期且七天权益仍有效时只用当前设备密钥取得下一张试用许可证；永久 PRO 不安排续签定时器或离线宽限，不引入轮询、WorkManager 或常驻线程。
8. Release 构建固定使用 R8 优化、混淆和资源收缩，产出映射文件只用于内部崩溃还原；正式包不可调试、不可 JNI 调试，当前 signer 不匹配时商业运行时 fail closed。签名摘要和许可证公钥均属于公开信任材料，不把它们伪装成客户端秘密。

## 6. 歌词匹配与网络不变量

1. 缓存未命中时并发启动 LRCLIB 精确单条，以及 QQ 音乐、网易云各自搜索计划的第一项；结果按实际完成顺序进入本地核验，不设置等待所有首轮来源的同步屏障。目录搜索计划每个来源最多三项，固定按“标题 + 原始歌手、标题 + 专辑核心、标题 + 歌手完整主体、仅标题”生成、去重并截断；前一项没有可获取正文的合格候选时，该来源立即推进下一项。任一结果必须通过录音核验且包含同步歌词，才能进入最终选择。
2. 正式歌词匹配只接受已知时长（至少 `1000 ms`），候选与当前播放时长差不得超过 `2000 ms`。现场、混音、重制、伴奏、翻唱、语言版等录音版本并入标题证据：双方版本类别相同或都未标注为 `EXACT`，仅一侧标注为 `NEAR`，双方都明确标注且类别不同为 `DIFFERENT`。只有明确版本冲突才拒绝；同类版本的地点、年份等附加描述可继续比较。时长和明确版本冲突是录音边界，不能被其它名称证据或来源数量抵消。
3. 标题、歌手和专辑统一形成 `EXACT / NEAR / UNKNOWN / DIFFERENT` 四级证据，并保留归一相等、发行核心、连续主体、编辑相似、跨文字未知、版本省略或明确冲突等具体原因。时长和已确认标题是硬门槛；标题中的明确版本冲突归入 `DIFFERENT`，歌手为 `DIFFERENT` 时也一律拒绝，二者都不能被专辑相等或来源数量抵消。通过硬门槛后，候选还必须满足“歌手已确认、专辑已确认、或两个独立来源共同补充 `UNKNOWN`”之一。标题 `4 / 3 / 0 / -5`、歌手 `3 / 2 / 0 / -2`、专辑 `3 / 2 / 0 / -1` 和独立来源 `+2` 只用于已合格候选排序，不再充当准入阈值；同一来源重复结果不算独立证明。
4. 近似文本先做 Unicode、大小写、标点、空格和重音归一；标题、歌手、专辑的编辑相似阈值分别为 `85% / 90% / 80%`，且至少 `8` 个归一化字符才启用编辑距离。标题主体与歌手展示名在压平前按空格、点、下划线、连字符及文字体系切换保留有序分段：一方完整分段序列连续包含于另一方，或双方共享占主体的连续分段且剩余部分只是跨文字展示时记为近似。格式符本身不进入全文比较，分隔后的多段可以组合成连续主体，但不得改写为合作歌手；没有明确分段的同文字任意字符子串和非连续片段拼接不得据此入选。专辑核心文本覆盖达到 `70%` 可视为近似；末尾由破折号、冒号或括号独立分隔的 `Single / EP` 属于发行类型，剥离后核心专辑名完全相等可记为近似，无独立分隔的普通专辑词不得剥离。明确双语括号标题可为跨文字标题提供等价桥接。跨文字体系且没有桥接时记为 `UNKNOWN`，只表示等待更多标题证据：不得单独入选、不得参与来源共识，也不能只凭歌手、专辑和时长补足。不维护人物、歌手或歌曲特判表。
5. `feat.`、`ft.`、`featuring`、`with` 属于合作歌手信息，不属于录音版本；允许该信息在标题括号与歌手栏之间移动，也允许来源省略已明确标注的合作歌手。普通标题括号附注不作硬门槛；合格候选先按版本证据 `EXACT -> NEAR`，再按排序分、括号信息“完全一致、相似或省略、完全不一致”、独立来源数、时长差、来源和来源曲目 ID 排序，使已有明确同版候选优先于单侧省略版本的候选，但不阻断后者作为单来源结果。
6. LRCLIB 精确请求使用标题主体、有效歌手（含标题中的合作歌手）、剥离独立 `Single / EP` 发行后缀后的专辑核心文本和毫秒时长换算值，只返回单条结果。精确结果单独合格时立即返回，单独不足时保留到后续已完成目录候选共同核验。QQ / 网易云某项目录结果没有合格候选时立即推进本来源下一项；有合格候选时先读取正文，正文为空后继续本来源剩余计划。最多并行两条不同来源正文通道，首个有效同步歌词立即返回；LRCLIB 精确请求与所有目录计划均已完成且没有正文在途，或到达 `1800ms` 首轮截止仍未解决时，才启动 LRCLIB 模糊列表。所有路径共享原总截止和正文通道。
7. 精确与目录首轮截止 `1800 ms`，单次查询总截止 `3800 ms`；连接超时 `1500 ms`，读取超时 `2200 ms`，封面总截止 `3000 ms`，单响应最大 `2 MiB`。瞬时失败只在当前请求仍为最新时等待 `1000ms` 并完整重试一次；代码中不得加入其它 `sleep` 或人为等待。远程封面只在最终歌词结果未携带封面时补查，不与歌词正文争抢首轮通道。
8. 每次在线入选必须携带当前匹配策略版本及最多两条支持候选；组合证据只复用已返回目录，不增加证明请求。占位歌手、空内容、`null`、`[object Object]` 和普通无时间轴歌词不得进入顶栏同步歌词主链；WebView 不得绕过原生解析主链直接请求歌词源。解析日志记录查询种类、候选数量、正文是否为空、耗时，以及最多前三条候选的拒绝原因、证据等级和独立来源数；不记录歌词正文或完整播放历史。
9. QQ 只读取歌词响应中的 `trans`，网易云只读取同一响应中的 `tlyric.lyric`；翻译必须自身包含同步时间轴才可进入结果。翻译不改变 LRCLIB 精确短路、候选排序、请求数量或截止时间，也不替换已经确认的原歌词来源。
10. 呈现层以归一化毫秒时间戳配对原文与翻译，最大差值为 `120ms`；每个原文和翻译行最多使用一次，缺行不得按数组序号顺延，翻译时间不得改变原文的活动行判定。
11. 人工目录搜索总截止与正文加载截止均为 `3800ms`；目录阶段不得预取歌词正文。人工候选可以与当前元数据不满足自动准入，但必须具有来源和来源 ID；用户点选后的正文仍必须通过同步时间轴分类，才能进入人工缓存。

## 7. 缓存不变量

1. 自动与人工歌词缓存共享 `128 MiB` 逻辑上限，触发清理后目标为上限的 `90%`；优先按既有淘汰分清理自动缓存，仍超限时再按更新时间清理旧人工覆盖。自动缓存每批最多淘汰 `256` 条，人工覆盖最多保留 `128` 首。
2. `recording_key` 使用与录音 tracker 一致的 `normalizeText` 三字段及毫秒时长的秒桶，旧 `cache_key` 仅作为行地址。读取在正负 `2` 秒索引窗口定位候选后，再按实际毫秒时长差不超过 `2000ms` 与完整入选证明复核；删除复用同一候选与毫秒校验。新写入在事务中收敛同一归一键的旧地址，并按实际删除字节修正统计。在线依赖双来源或双语标题桥接的结果不得在缓存读取时被降成单来源判断；匹配语义变化时递增策略版本，不为兼容旧结论绕过当前选择器。
3. `30` 天后允许刷新歌词；访问频率最多累计 `30` 次，每次为淘汰分增加 `7` 天权重。
4. 读取优先级固定为“人工覆盖 > 自动缓存 > 在线自动匹配”。人工覆盖按当前播放身份写入独立表，不伪造自动入选证明、不受 `30` 天刷新影响；删除人工覆盖后原自动缓存继续有效。缓存策略与空间阈值只由 `LyricsCache` / `LyricsCachePolicy` 管理，服务层不得复制。
5. 当前数据库版本为 `6`：自动载荷同时保存查询身份与入选证明，两张表各持有唯一归一 `recording_key` 索引。`4 -> 5` 重放完整证明及旧键绑定；`5 -> 6` 从可验证的旧查询身份重建索引，无法证明的自动条目清理，人工原始键、正文、时间和字节数保留，无法索引的人工记录仍保留。合计统计在迁移事务重算。历史版本 `3` 清理无证明缓存，版本 `4` 创建人工覆盖表，再按当前规则升级。翻译仍为可选字段；有效载荷缺少翻译字段时先返回原文并只触发一次后台刷新。
6. 缓存读取、写入及对应摘要由 Store 在同一串行操作内取得并发布；自动写入必须回读，不能把在线歌词冒充持久缓存。已加载但未持久化的歌词标记 `ONLINE_ONLY`，缓存读取中标记 `LOADING`；人工结果优先于晚到自动结果，删除或切歌后的已取消任务不得重新写回。
